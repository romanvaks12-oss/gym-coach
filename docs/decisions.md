# Решения (ADR)

Формат: `## ADR-NNN — Название` + Контекст / Решение / Последствия / Дата.
Статус: `proposed` | `accepted` | `superseded`.

## ADR-001 — PWA на GitHub Pages

**Статус:** accepted (2026-10-25)
**Контекст:** заказчик не разработчик, нужен ввод с iPhone в зале, таблицы и графики, всё бесплатно,
без выделенного сервера. Нативное iOS-приложение требует Mac и $99/год.
**Решение:** PWA (React + TypeScript, Vite), статика на GitHub Pages, иконка на домашнем экране.
**Последствия:** работает офлайн, ноль расходов, Mac не нужен. Ограничения iOS (нет фоновой
синхронизации, нет пуш-уведомлений в старых версиях) принимаем. Тот же фронтенд позже можно
завернуть в Telegram Mini App без переписывания.

## ADR-002 — Данные: локально первично, Google Sheets как хранилище-зеркало

**Статус:** accepted (2026-10-25)
**Контекст:** выбрана Google Sheets как база (привычные таблицы, доступ с компьютера).
Но Web App отвечает 0,3–2 с, а в зале сеть нестабильна.
**Решение:** IndexedDB — оперативное хранилище и источник для UI; Google Sheets через Apps Script —
долговременное хранилище и синк, запись батчами с флагом `pendingSync`.
**Последствия:** быстрый интерфейс и офлайн; нужна аккуратная дедупликация по `id` и `updatedAt`.
URL Web App и токен хранятся в localStorage телефона (в репозиторий не попадают).
Риск: любой, кто узнает URL `/exec`, сможет вызвать API — поэтому обязательный токен в запросе.

## ADR-003 — Без ИИ на старте

**Статус:** accepted (2026-10-25)
**Контекст:** нужен предсказуемый результат и минимум зависимостей.
**Решение:** план считает детерминированный движок правил (`src/core/`). ИИ — отдельная фаза P3
как надстройка: объяснения, нестандартные ситуации. Приложение обязано работать без ИИ.
**Последствия:** нет расходов и утечек ключей на старте; логика покрывается тестами.

## ADR-004 — Стек: Vite + React + TypeScript

**Статус:** accepted (2026-10-25)
**Решение:** SPA на Vite, React 18, TypeScript strict, Vitest для `src/core/`, без UI-библиотек
(свои компоненты, CSS-переменные). Навигация — табы в состоянии, без роутера; frontend-роутер
добавим только если появятся deep links (тогда HashRouter — требование GitHub Pages).
**Последствия:** нужен Node.js на машине, `npm install` / `npm run dev`. Зато типы ловят половину ошибок.

## ADR-007 — Иллюстрации упражнений и карта мышц

**Статус:** accepted (2026-10-25)
**Контекст:** нужны картинки «как делать» и подсветка работающих мышц, без платных библиотек и без
хранения десятков мегабайт в репозитории.
**Решение:**
1. Фото старт/финиш — из публичного каталога `yuhonas/free-exercise-db` (лицензия Unlicense,
   public domain, 876 упражнений). Файлы не копируем в репозиторий, берём по CDN jsDelivr.
   Соответствие нашим 58 упражнениям — в `src/data/exercise-media.json`, генерируется
   скриптом `tools/match-exercise-media.mjs` (58/58 совпадений).
2. Карта мышц — свой SVG (`src/components/MuscleMap.tsx`): перед/спина, подсветка основной группы
   сплошным акцентом, вспомогательных — полупрозрачным. Не зависит от лицензий и всегда в тон теме.
3. Силуэт — анатомический плакат в стиле дочи / Вадима Иванова: контурная линия, «мясные» зоны
   отдельными формами, детализация (дельты, верх/низ груди, 8 сегментов пресса + косые + зубчатые,
   трапеции, широчайшие, разгибатели, трицепс/бицепс бедра по головкам, ягодицы, икры). Рисуем
   левую половину и зеркалим (`translate(200,0) scale(-1,1)`), сетка 200×460. Подпись под картой:
   «контур — в память о Вадиме Иванове».
**Последствия:** первая загрузка картинки — сеть (≈70 КБ на кадр), поэтому в каталоге превью
ленивые, в шторке упражнения — приоритетные. Полный офлайн картинок не гарантируем; текст и карта
мышц работают всегда. Если CDN станет недоступен — карта мышц и подсказки остаются.
Карта — вектор: правится путями, весит меньше килобайта, масштабируется без размытия.

## ADR-008 — Сплит как скелет + фильтр восстановления

**Статус:** accepted (2026-10-26)
**Контекст:** чистый «выбор по восстановлению» (что свежее — то и тренируем) легко приводит к двум
тренировкам спины подряд и к неделе без ног. Чистый сплит игнорирует самочувствие. Заказчик хочет
и структуру, и запрет грузить группу, которая тренировалась вчера.
**Решение:** программа — скелет из трёх шаблонов (всё тело / верх / низ). Перед выбором дня движок:
1) убирает упражнения на группы из брифа с болезненностью 7–10 и на группы, которым меньше
`daysUntilRecovered` дней отдыха (крупные: 2 дня, мелкие: 1);
2) оценивает шаблон по «свежести» готовых групп;
3) добавляет бонус дню, который логично идёт после прошлой тренировки (`upper → lower`);
4) когда история уже есть, «всё тело» — запасной вариант (штраф −1,5), основные — верх/низ.
Тип последней тренировки хранится в `meta.lastDay` (`storage/history.ts`), ротация действует 3 дня.
**Последствия:** программа не прыгает хаотично, спина/ноги не грузятся два дня подряд, болезненная
группа просто выпадает из дня. Минус: если вчера был верх, сегодня будет низ или отдых — «свободного
творчества» меньше. Полноценные Upper A/B и Lower A/B (разные упражнения в двух днях) — следующий шаг.

## ADR-009 — Разминка, вес тела и упражнения «на время»

**Статус:** accepted (2026-10-26)
**Контекст:** заказчик возразил против блока разминки (часть подходов выглядела как рабочие), попросил
учитывать вес тела в подтягиваниях и заметил, что у планки не бывает «веса и 10 повторов».
**Решение:**
1. Блок разминки из экрана тренировки убран; в лог пишутся только рабочие подходы (`isWarmup` остаётся
   в схеме для будущего, функция `warmupSets` сохранена в `core/progression.ts` как справка).
2. Вес тела вводится в брифе, сохраняется в store `body` (`date-weight`) — это ещё и замер для графика.
3. Подтягивания/брусья/отжимания: ввод «свой вес + доп. вес», тоннаж = (вес тела + доп. вес) × повторы,
   прогрессия по повторам. Подтягивания: 2–3 повтора, максимум 3 подхода.
4. Планка и прогулка фермера — `measure: "time"`, 30–45 секунд, прогрессия по секундам.
**Последствия:** данные совместимы со старой схемой (поля опциональны). Вес тела нужен перед каждой
тренировкой, иначе тоннаж своих весов считается без него (0).

## ADR-010 — Правка записанного подхода и защита от опечаток

**Статус:** accepted (2026-10-26)
**Контекст:** в зале легко нажать лишнюю цифру: записали 112 кг вместо 12 — и подход уже в базе,
исправить нечем. Ошибочные данные портят прогрессию и тоннаж.
**Решение:**
1. Каждый записанный подход можно открыть («правка»): меняются вес, повторы/секунды и RPE, номер
   подхода и `id` сохраняются; есть удаление с перенумерацией оставшихся.
2. Чистая функция `checkSetInput` (`src/core/validation.ts`) проверяет ввод до записи: вес 0–400 кг,
   повторы 1–100 (целые), время 1–1800 с, RPE 1–10. За пределами — ошибка, запись блокируется.
3. Мягкое предупреждение при скачке веса больше «прошлый × 1,3 + 15 кг»: показываем текст и просим
   нажать «Всё верно, записать» второй раз. Так ловится 12 → 112, но обычная прибавка не мешает.
4. Тоннаж и прогрессия считаются по исправленным данным: логи не дублируются, правка не создаёт
   новый `id`.
**Последствия:** пользователь может ошибиться без последствий. Предупреждение — не блокировка:
решение всегда за человеком. Валидация не мешает своим весом (0 кг разрешён) и упражнениям на время.

## ADR-011 — Публичный репозиторий, мягкий код доступа, аккаунты отложены

**Статус:** accepted (2026-10-26)
**Контекст:** GitHub Pages на бесплатном тарифе публикует только публичные репозитории.
Данные тренировок локальные, сервера и аккаунтов нет. Нужно показать приложение друзьям
на тестовый период, не усложнив вход себе, и понимать путь масштабирования.
**Решение:**
1. Репозиторий остаётся публичным: Pages и Actions бесплатны, секретов в коде нет. Код
   фронтенда всё равно скачивается в браузер, поэтому закрытие репозитория приложение не
   прячет; права фиксирует `LICENSE` («все права защищены»).
2. Данные не покидают устройство. До P2.5 единственный путь наружу — экспорт JSON.
3. Тестовый доступ — необязательный код: `VITE_INVITE_CODE` из переменной GitHub Actions
   `INVITE_CODE`. Пусто → приложение открывается сразу, без экрана входа. Ввод один раз,
   запоминается в localStorage. Это шторка, а не защита: код попадает в бандл.
4. Настоящая проверка на сервере (Cloudflare Worker + подписанная cookie) — только если
   тестеров станет много или понадобится отзывать доступ. Решение отложено.
5. Аккаунты и синк между устройствами — после P2.5, на Supabase free или Cloudflare D1.
   `pendingSync` в схеме уже есть.
**Последствия:** нулевая стоимость и нулевое трение для владельца, друзьям достаточно ссылки.
Секреты нельзя класть в код — только в localStorage или в переменные GitHub. Подробности и
чек-лист — `docs/access.md`.

## ADR-012 — Google Sheets как зеркало: Apps Script вместо сервера

**Статус:** accepted (2026-10-26)
**Контекст:** данные лежат в IndexedDB одного браузера. Смена телефона, чистка Safari или
«удалил с домашнего экрана» = потеря истории. Полноценный бэкенд стоит денег и требует карты,
а пользователь не разработчик.
**Решение:**
1. Источник истины — IndexedDB. Google Sheets — зеркало и архив: приложение полностью работает
   без сети и без таблицы.
2. Транспорт — Apps Script Web App (`integrations/apps-script/Code.gs`): `ping`, `pull`, `push`.
   Тело запроса — `text/plain` с JSON внутри, чтобы не ловить CORS-предзапрос; Apps Script не
   отдаёт HTTP-статусы, поэтому клиент читает `{ok:true|false, error}` из тела.
3. Токен и URL — только в `localStorage` телефона и в скрипте таблицы. В репозитории их нет.
   `TOKEN` не заменён → сервер отвечает `token_not_configured` (защита от случайного развёртывания).
4. Слияние — по `id` (`src/core/merge.ts`): побеждает более свежий `updatedAt`, но запись с
   `pendingSync` всегда главнее серверной. Сначала push, потом полный pull и merge, затем
   локальные копии помечаются отправленными.
5. Запись батчами в одной транзакции (`putMany`), `LockService` на стороне скрипта, даты — текстом,
   чтобы Sheets не сдвигал дни в своём часовом поясе.
6. Синк не удаляет строки: удалённый в приложении подход остаётся в таблице как архив.
7. Автосинк после «Завершить тренировку» — тихий: сводка показывается сразу, ошибка не блокирует,
   на экране есть «Отправить ещё раз». Ручной синк и проверка связи — в «Настройках».
**Последствия:** бесплатно и без карты, данные видны с компьютера и переживают смену устройства.
Ограничения: квоты Google (хватает с запасом для одного человека), после смены токена нужно новое
развёртывание, старые версии `Code.gs` не знают новых действий. Инструкция для не-разработчика —
`docs/sheets-setup.md`.

## ADR-013 — «Загрузить из таблицы»: замена локальных данных серверными

**Статус:** accepted (2026-10-29)
**Контекст:** после переустановки PWA IndexedDB пустая, а обычный `syncNow` тянет данные только
через слияние и не помогает, если локальная база засорена тестовыми тренировками. Пользователю
нужен способ «взять всё из таблицы и забыть, что было на этом устройстве».
**Решение:**
1. `pullReplace` (`src/storage/sync.ts`) читает таблицу и **заменяет** `workouts`/`sets`/`body`
   целиком: сначала `db.clear`, потом `putMany`.
2. Защита от пустого ответа: если в таблице нет ни одной тренировки, локальные данные не трогаются
   (иначе кривой URL стирал бы историю).
3. Подходы без своей тренировки в таблице отбрасываются — половинчатых записей не бывает.
4. Кнопка «Загрузить из таблицы» требует второго нажатия («Точно заменить?»), потому что действие
   необратимо.
5. Если база пустая и синк настроен, история подтягивается сама: на экране «Настройки» при
   открытии и после «Проверить связь». Это закрывает сценарий «новый телефон».
**Последствия:** тестовые записи убираются одним нажатием, а после переустановки PWA история
возвращается без ручных действий. Строки, удалённые в таблице, после такой загрузки исчезают и на
устройстве.

## ADR-014 — дополнительное упражнение в конце тренировки и горизонтальный «Прогресс»

**Статус:** accepted (2026-10-31)
**Контекст:** в зале бывает лишнее время и желание добить мелкие группы (предплечья, трапеции,
икры), но план уже собран. Раньше единственным способом было записать подход «не туда» или
бросить тренировку незавершённой. Плюс на компьютере «Прогресс» выглядел как длинная телефонная
колонка, хотя там много свободного места.
**Решение:**
1. Кнопка «+ Добавить упражнение» в `WorkoutRunner` открывает `ExtraExerciseSheet`: поиск, чипсы
   по группам мышц, список с рекомендацией «3 × 8–12 · 20 кг · RPE 8».
2. Рекомендация считается тем же `buildPlanItem` (`src/core/plan.ts`), что и основной план, —
   прогрессия, RPE и объём дня подчиняются общей логике, отдельного «второго» алгоритма нет.
3. Добавленное упражнение дописывается в `items` (локальное состояние раннера) и сохраняется в
   `ActiveSession.plan.items` через `onProgress(index, logs, items)` — перезагрузка страницы
   посреди тренировки не теряет доп. упражнение. В шапке оно помечается «· добавлено».
4. Уже добавленные упражнения в списке не предлагаются (`usedIds`).
5. «Прогресс» получил горизонтальную раскладку на контейнерном запросе `.progress-scope`
   (≥760 px): две колонки, слева обзор и графики, справа детали. На телефоне и в превью 390 px
   раскладка остаётся одноколоночной, поэтому мобильный экран не пострадал.
6. Кликабельность: плитки показателей прокручивают к своей карточке, полосы групп мышц
   раскрывают разбивку по упражнениям, личные рекорды открывают график 1ПМ этого упражнения.
**Последствия:** тренировку можно добрать на месте, не ломая план; на компьютере видно вдвое
больше без прокрутки. Ограничение: доп. упражнение не попадает в `planId`-шаблон, то есть в
следующий план автоматически не переносится — оно влияет только на историю и рекомендации.
